Why AIRP's shared graph state is a TypedDict, not a Pydantic model

Eight agents read and write one shared state object on every node transition. Here's why validation lives at the edges instead of on the state itself.

Every node in AIRP's LangGraph pipeline reads from and writes back into one shared state object: the orchestrator, all four research agents, the Contrarian, Risk Officer, Valuation Agent, and Portfolio Manager. No agent-to-agent messaging happens outside of it. That object is a plain TypedDict, not a Pydantic BaseModel, which looks like the wrong call for anything carrying LLM-generated content until you look at where the validation actually happens instead.

The framework constraint

LangGraph's StateGraph expects dict-compatible state; that's the shape it diffs and merges between nodes. A TypedDict gives static type checking at the point every field is read or written in code, with no runtime object construction on a path that gets touched at every single node transition, and in an 8-agent graph with a debate loop, that path runs a lot.

Where validation actually happens

It doesn't disappear, it just doesn't live on the container. Every agent's own output is a Pydantic model internally (ContrarianReport, the fundamental analyst's output schema, and so on), and gets fully validated the moment it's constructed. Only after that does it get serialized with model.model_dump() and written into the shared dict as plain data. The untrusted part, an LLM's structured output, gets checked exactly once, at the boundary where it enters the system. The state object itself is just the pipe it flows through afterward.

total=False, on purpose

The TypedDict is declared with total=False. Almost every field starts empty and gets populated progressively as the pipeline runs: a research agent's output doesn't exist yet at the planner node, and the debate transcript doesn't exist until round one finishes. total=False makes every field implicitly optional, so reading a not-yet-populated key doesn't throw partway through a run that's still in progress.

The safety net that replaces runtime validation

Giving up per-access validation on the state dict means giving up the guarantee that everything in it is JSON-serializable, and state gets persisted to PostgreSQL after every node so a failed run can resume instead of restarting. That guarantee is enforced a different way: a round-trip contract, json.loads(json.dumps(state, default=str)), checked by tests against a fully-populated state. A field that can't survive that round-trip fails at commit time, in CI, not at 2am when a resumed run tries to reload a state snapshot that was never actually serializable in the first place.

The trade-off

This gives up runtime safety on the state object itself: nothing stops a future node from writing a non-serializable value into a random key, in theory. In practice, the two things that guarantee actually needs to protect (agent output validity and persistence safety) are both covered, just at the boundary and in tests instead of on every dict access. The alternative was paying Pydantic's construction and validation cost on every one of dozens of node transitions per run, to protect an invariant that a cheaper check already covers.
