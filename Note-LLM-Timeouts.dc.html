Why every LLM call in AIRP has an explicit, bounded timeout

A node once hung with zero log output, well past its own soft timeout. The fix, and why a node-level watchdog alone can't catch this.

AIRP's pipeline enforces a per-node soft timeout so one slow agent can't stall the whole 90-second run. It's a reasonable safety net. Until a node hangs anyway, well past that timeout, with zero log output, no timeout warning, and no traceback. Nothing on-screen says why. The pipeline just doesn't come back.

Why the node-level timeout didn't catch it

The node timeout is a soft, thread-based watchdog: it can only detect an overrun after control returns to Python from whatever call is currently blocking. If that call is stuck inside the underlying LLM SDK's own HTTP client (not raising, not returning, just sitting on a socket), the watchdog has nothing to interrupt. It's waiting for a return that isn't going to come on its own schedule. Meanwhile langchain_groq and langchain_anthropic, left unconfigured, fall back to the SDK's own default timeout, which isn't guaranteed to be bounded at all.

The actual fix

Every LLM client AIRP constructs gets an explicit HTTP-level timeout, capped at 25 seconds (under the pipeline's own 30-second soft node timeout), set directly at client construction, plus max_retries=1. The ordering matters: 25s is deliberately less than 30s so the client itself raises before the node-level watchdog would ever need to fire. The failure becomes a normal exception in a place the code already expects one, not a hang the watchdog has to detect after the fact.

Why max_retries=1 matters just as much

Without it, the SDK's own internal retry and backoff on a 429 can silently turn one 25-second timeout into several, stacking into 60-90+ seconds across attempts before AIRP's own per-agent try/except graceful-degradation logic ever sees the exception. Capping retries at the client level means that logic sees the failure on the first bounded attempt, not several silent retries later.

The payoff

A slow or rate-limited provider now degrades exactly one agent's output, caught by that agent's own try/except just like any other failure mode already built into the pipeline, instead of freezing the entire 8-agent run with no signal about which node, or why. It turned a debugging session with zero log output into a stack trace pointing at the exact call that failed.
